Regulated Architecture: Designing for MASAK, KVKK, and Multi-Locale Runtimes

How strict design token typing and component boundaries eliminate compliance risks, prevent runtime internationalization traps, and guarantee accessibility across high-stakes banking and insurance ecosystems.

The Cost of Non-Compliance in Financial UX

In regulated insurtech and banking environments (governed under MASAK, KVKK, SPK, and European GDPR frameworks), a design mistake is not an aesthetic flaw—it is a legal violation carrying multimillion-dollar regulatory fines.

When software teams rely on ad-hoc frontend code to mask national identification numbers (TCKN), IBANs, or tax IDs, edge cases inevitably leak unmasked data into browser DOM trees, audit logs, or client-side analytics trackers.

“In regulated enterprise software, compliance is not a post-launch audit checklist; it is an invariant baked directly into component typography, data tokens, and input masking architectures.”

The Turkish Dotted-i Runtime Casing Trap

One of the most notorious bugs in global enterprise software involves the Turkish dotted and dotless I (İ/i vs. I/ı). Standard JavaScript transformations such as toLowerCase() or CSS text-transform: uppercase mutate Turkish characters unpredictably (e.g. converting "DİCLE" to "d\u0131cle" rather than "dicle").

In insurance search queries and policy lookup keys, this casing mutation causes silent query failures and broken customer records. Our design architecture eliminates this at the foundational level by prohibiting raw CSS text transforms on user data and enforcing locale-aware runtime string formatting (toLocaleUpperCase('tr-TR')) across all input components.

The Universal Derived Field & KVKK Data Masking

To prevent developers from inventing arbitrary grey boxes or disabled inputs for sensitive read-only identifiers, we standardized the AgitoDerivedField component:

1. Built-in Regulatory Masking: Sensitive fields (TCKN, credit card tokens, IBANs) automatically render masked values (e.g., *** *** 4821) with role-based unmask toggles tied to audit logging.

2. High-Contrast WCAG 2.1 AA/AAA Compliance: Rather than low-contrast disabled grey text (#A1A1AA) which fails accessibility audits, derived fields use a subtle 12px label above a crisp 14px primary text string with a 1px baseline border.

3. Multi-Currency Alignment: Numeric inputs strictly separate monetary values from currency ISO codes (TRY, USD, EUR), preventing floating-point rounding errors and international ledger misalignment.
